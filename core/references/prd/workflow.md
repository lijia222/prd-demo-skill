# `prd` 模块：新建 PRD 工作流

## 适用范围

用于新需求、首版大纲、首版详写和套件级结构重组。已有 PRD 的局部规则、字段、流程或文案修改交给 `change-sync`；Frozen 的任何改动也交给 `change-sync`。

## 阶段 0：环境和意图

- 确认当前项目根目录、说明文件、PRD/Demo 规范和目标版本。
- 确认用户要新建，而不是修改已有文件。
- 检查用户给出的文件清单；没有明确授权不得增加制品。
- 有背景材料时先区分证据、草案、策略和开发权威；未升格材料不能直接作为开发规则。

## 阶段 1：澄清

先输出推断场景，再提问题：一般每轮 1～3 问；用户要求一次一问时只问 1 个。至少确认：

- 场景、目标用户、核心痛点和主读者。
- 是否有基线、基线路径和本次真实差量。
- 文档形态 A-F、单体/轻套件/全套件。
- 是否需要故事地图；开发 PRD 默认不强制用户故事章。
- 外部依赖、待决项和验收方向。

有基线时，写目录前把结论分为五桶：真增量、现网对齐、技术自决、后期预埋、过程废案。现网对齐只进复用清单，不单独成章；过程废案不进 PRD。

## 阶段 2：拆分和形态

| 形态 | 适用 |
|---|---|
| A 套件导航 | 多读者、需要索引和硬约束 |
| B 页面模块 | 无基线的完整 UI 与操作 |
| C 契约接入 | 无基线的跨服务数据和状态 |
| D 增量改动 | 有基线的字段、规则、入口或对接差量，默认优先 |
| E 分析报表 | 指标和布局为主 |
| F 一页纸/发布 | 导航、归档或上线清单 |

拆分信号包括字段重复、独立上线、独立状态机、评审人不同、跨平台复用和跨服务契约。套件必须有权威地图；轻套件可以使用子文档互链。

## 阶段 3：目录和术语冻结

- 提案 3～8 节目录，用户确认后再详写。
- 术语表建议 5～15 个词；确定中文主名、技术名、层级、时间/金额/状态口径。
- D 形态必须有“现网复用清单”，只列沿用能力，不重复现网正文。
- 每个可执行规则域只能有一个权威文档；其他文档只链接和摘要。

## 阶段 4：详写门禁

每篇 PRD 必须包含：

1. 文首元信息（版本、状态、读者/范围、相关链接）。
2. 一句话定位。
3. 范围边界、兄弟文档边界或复用清单。
4. 主规则或主流程（流程使用 Mermaid）。
5. 可测验收。
6. 权威声明和交叉链接。
7. CHANGELOG 或版本记录入口。

正文要求：标题直白、术语一致、时间/金额/状态口径明确、同主题合并、多路径使用分路径短文和结果表，不把示例写成正式建模规则，不强制创建无必要的 Demo。

## 完成后

套件同步检查版本指针、权威地图、术语和变更记录。纯契约需求不强推 Demo；有页面时只建议进入 `demo`，不自动连环执行。后续局部修改统一进入 `change-sync`。
